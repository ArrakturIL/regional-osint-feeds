# REGIONAL WATCH — стиль отчётов и восстановление контекста

> **Постоянная инструкция для всех чатов и агентов, работающих с REGIONAL WATCH.**
> Актуальные факты, технический статус и задачи берутся из [MASTER TODO](MASTER_TODO_HISTORY_2026-11-17.md) в ветке `main`, а не из этого файла и не из прошлого ответа.

## Зачем

Владелец проекта подтвердил 17.11.2026, что формат короткого итогового сообщения после ARCH-03 является **предпочтительным по умолчанию**. Он должен сохраняться при смене чата, обрыве контекста и передаче работы между агентами.

## Формат ответа по умолчанию

1. **Сразу результат**: «**ARCH-03 официально закрыт.** ✅», «**ARCH-07 — проверка не прошла.** ⚠️», «**ARCH-05 — ожидаем отложенной приёмки.**» либо точный аналог. Не подменять фактическое выполнение намерением. Если вопрос простой, ответить просто и кратко, без искусственного отчёта.
2. **Одним коротким абзацем — проверяемое доказательство**: сколько тестов/заданий прошло, точная ссылка на CI/PR/коммит/production postcheck, только если действительно подтверждено в текущем прогоне. Не выдавать зелёный CI за живой QA или production deployment.
3. **Одной фразой — что зафиксировано**: ссылка на изменённый MASTER TODO, отчёт, PR или другую каноническую запись. Не утверждать, что изменил файл, пока GitHub не подтвердил запись.
4. **Короткая подборка статусов**, только если помогает (обычно 2–4 пункта): ✅ закрыто; ◐ выполнено и ждёт независимой приёмки; ⏳ ожидает отчёта; ○ следующая задача. Различать «закончили разработку» и «этап полностью принят».
5. **Последней строкой — важная граница**: что реально изменено и не изменено (PR открыт/merged, prod deployed или нет, D1/AI/cron/секреты не трогали) и ближайший следующий этап, только если он уже согласован.

### Шаблон успешного итогового отчёта

```markdown
**ARCH-XX официально закрыт.** ✅

[Короткий конкретный результат.] [Полный CI #…](https://github.com/ArrakturIL/regional-osint-feeds/actions/runs/…) — **SUCCESS**, [N/N] тестов/заданий пройдено. [При необходимости — независимая production-проверка].

Результат внесён в [MASTER TODO](https://github.com/ArrakturIL/regional-osint-feeds/blob/main/docs/REGIONAL_WATCH_MASTER_TODO.md) и [отчёт/PR]([проверенная ссылка]).

- ✅ **ARCH-XX** — закрыт.
- ⏳ **ARCH-YY** — реализация сделана; ждём запланированную проверку.
- ○ **ARCH-ZZ** — следующий активный этап.

**Граница:** PR [номер и действительное состояние], production [точный статус]. [Что не меняли, если это важно].
```

Это **образец ритма и компактности**, не требование печатать пять блоков даже при ответе на «почему частично?». Доказательства и формулировки выбираются по фактам, не копируются из шаблона. Ссылки и количества нельзя выдумывать.

### Когда задача не завершена или тесты красные

```markdown
**ARCH-XX — пока не закрыт.** ⚠️

Проверка [реальная ссылка] обнаружила [конкретную причину]. Из [N] тестов [K] не прошли; успешные части — [кратко].

В [MASTER TODO] отмечено: частично / заблокировано, [точная запись если создана].

**Граница:** production не менялся / изменился [фактическое состояние]. Следующий согласованный шаг — [что именно].
```

Не использовать большую таблицу для короткого обновления. Таблицы, счётчики и более выразительное оформление уместны при запросе прогресса **всего проекта**, когда это экономит чтение; простые итоги — связные абзацы и один короткий список.

## Тон и объём

- **По-русски, на «ты», естественно и без официоза.** Нормально говорить «проверил», «закрыл», «не трогал», а не «осуществлена имплементация».
- Не начинать с пересказа поручения, бесполезного плана, фразы «я понял». Не писать длинные служебные сводки, когда достаточно двух абзацев.
- Без лести, самооправданий и ненужных лекций. Ответить на фактическое намерение: разговор — разговором, отчёт — отчётом.
- Точность важнее красивого оформления: **код готов ≠ PR merged ≠ production deployed ≠ отложенная live-приёмка прошла**.
- По возможности давать **точные ссылки** на GitHub CI/PR/отчёт и один канонический MASTER TODO. Не перегружать сырыми логами и внутренней терминологией без просьбы.
- Не навязывать новых задач или незапрошенных следующих шагов; если порядок уже утверждён, кратко назвать следующий этап.
- Использовать @superpowers и доступные профильные плагины при планировании, изменении кода и верификации, но не плодить лишних агентов и сетевых вызовов.

## Восстановление работы после смены чата

1. Открыть [корневые инструкции AGENTS.md](../../AGENTS.md) и **последние** статусы в [MASTER TODO](MASTER_TODO_HISTORY_2026-11-17.md) на `main`. Установить текущий фактический `main` HEAD, открытые PR и их HEAD/merge-state, последние GitHub CI. Прежние сообщения/память использовать как подсказку, не как доказательство.
2. Отделить **live production** от тестов в PR. Читать новейшие итоговые отчёты только по тем этапам, которые нужны; не переносить старые SHA, даты или цифры без проверки.
3. Для текущего периода разработки: ARCH-01/02/03/06 — завершены в заявленной технической области; ARCH-04 и ARCH-05 — выполненные правки, отдельно назначенные независимые проверки (20.11.2026 09:00 Israel и 18.11.2026 18:00 Israel), до отчётов без повторной разработки; ARCH-07 полностью закрыт после [PR #84](https://github.com/ArrakturIL/regional-osint-feeds/pull/84) merge, [coordinated CI #44009574048](https://github.com/ArrakturIL/regional-osint-feeds/actions/runs/44009574048) (12 executed successful jobs) и independent Cloudflare + production HTTP 200 postcheck; [финальный отчёт](../research/ARCH_07_FINAL_BACKEND_ACCEPTANCE_2026-11-17.md). **Это состояние на 17.11.2026, не вечная истина.**
4. Обновлять MASTER TODO после **фактически подтверждённых** операций; не выдавать 0 ошибок за полный UI QA. Без явного согласования не объединять PR, не выкатывать production, не трогать реальные D1/Neon/секреты/платные лимиты, не перезапускать уже назначенные проверки.
5. После любого выполнения отвечать в кратком стиле выше, с точным фактом и ссылкой.

Эти правила описывают **формат коммуникации**, а не отменяют более свежие решения владельца или инструкции ChatGPT-проекта.
